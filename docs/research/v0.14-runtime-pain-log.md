## Completed campaign observations

- **Runtime performance:** cheap 1-KiB compression loses; high-data 64-KiB level 1
  also loses to serial. Coarse work amortizes dispatch. Raw/native ordering varies,
  so no scheduler optimization follows.
- **Benchmark methodology:** the initial eight-worker case funded four maxima,
  and a finite 32-MiB source could undersupply offered concurrency 64. Preserve
  both, and use the seven-cell supplement with correctly funded workers and
  64-MiB queue source. These were harness controls, not runtime bugs.
- **Platform-specific behavior:** requested 1-ms consumer waits vary substantially
  on Windows. Count/byte/held controls have inconsistent throughput ordering;
  six causal prefill trials prove progress without relying on timer throughput.
- **Node/zlib API:** native async c4 is a strong baseline and has better FS p95
  than PJS four workers here; libuv isolation helps only under higher contention.
- **Documentation:** six fresh processes show why actual output credit cannot be
  sold as RSS savings. High upper/held/count RSS is nearly equal despite different
  credit semantics. Application-retained output and codec allocations remain outside.
- **Runtime ergonomics:** shared partition identity plus direct binary output
  reconstructs three actual parallel round trips, including partial tails.
  No ordered-stream or compression-specific protocol need emerged.
- **Runtime correctness:** none discovered. Bound/equality violations reject,
  queued/active cancellation, ungated native compression abort, consumer break,
  worker exit/replacement and terminal credit cleanup all pass. Runtime source stays frozen.

Final architectural gate: **no missing primitive**. Useful pipeline behavior and
telemetry/ownership documentation caveats support Outcome B; no package or runtime
feature is justified. Recommendations are recorded in the main report only.
